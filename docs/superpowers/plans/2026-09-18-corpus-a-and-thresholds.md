# Corpus A and the Threshold Pilot — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the labelled Spanish/English corpus this benchmark's
differential claim depends on, with labels auditable against a committed fact
ledger rather than asserted, and derive the star thresholds from the dumb
baseline alone before any competitor is measured.

**Architecture:** The fact ledger comes first and everything else is derived
from it: conversations are written to state its facts, questions are written to
ask about its facts, and the audit checks both against it. A label is then
checkable by a human against two artifacts rather than taken on trust. The
harness gains what the corpus needs and nothing more — unanswerable questions,
an as-of date, the fifth stratum, and a corpus the manifest can source rather
than only hash.

**Tech Stack:** Python 3.12+, uv, SQLite FTS5, pytest, codeality-py, ruff,
mypy. JSONL artifacts. Codex CLI for the blind critique pass.

**Spec:** `docs/superpowers/specs/2026-09-17-memory-bench-design.md` — sections
"Corpus A — synthetic, Spanish and English", "Scoring", "Declared bias" and
"Gates before any scored run".

## Global Constraints

- One exported unit and one primary responsibility per source file. A helper
  that is not the file's primary unit goes in its own file with an explicit
  import.
- `uv run pytest` passes, `uv run codeality-py check` reports 0 findings,
  `uv run codeality-py gate` stays green. Coverage threshold 80.
- Commit messages imperative, English, no assistant attribution, no co-author
  trailers.
- TDD: failing test, watch it fail, implement, watch it pass.
- Published shapes carry versions. `RAW_SCHEMA_VERSION` (`membench/write_run.py`),
  `ADAPTER_CONTRACT_VERSION` (`membench/memory_adapter.py`) and
  `MANIFEST_VERSION` (`membench/build_manifest.py`) each have a stated
  major/minor rule; obey it and record every change in the version's own
  changelog, including meaning changes to an existing field.
- No artifact may misrepresent its own run. A number that was not observed is
  `null`, never `0.0`; a rule that is scored is published in the contract; a
  claim in `README.md` or `TODO.md` must be true of the code as it stands.
- The corpus is Spanish **and** English, both first-class. Spanish text carries
  its real accents and `ñ`; the FTS5 tokenizer is pinned to
  `unicode61 remove_diacritics 2` precisely so it can.
- Strata vocabulary, fixed, five dimensions: language `es|en`; source shape
  `conversation|note`; vocabulary overlap with competing conversations
  `overlap|no-overlap`; age within the corpus `recent|old`; and
  `temporal-contradiction` where the corpus states a fact and later reverses
  it. `temporal-contradiction` is the one tag that is present or absent rather
  than one of a pair.

## Rulings made before this plan, binding on every task

**R1 — an unanswerable question is never averaged into recall or
`reciprocal_rank`.** It has no answer conversation, so recall is undefined for
it, and scoring an empty ranking as a hit would hand a perfect score to a
system that returns nothing at all. Unanswerable questions are their own
reported quantity — how often the system correctly returned nothing — and the
two populations are never merged, exactly as Track R and Track A are never
merged.

**R2 — the corpus does not claim bit-exact regeneration.** The spec says
"generated by Claude with a fixed seed". An agent-written corpus cannot honour
that, and claiming it would be the misrepresentation this repository exists to
refuse. What is committed instead: the corpus itself, the fact ledger it was
written from, the generation instructions, and a manifest entry that sources it
by repository, commit and path. Reproducing the *report* is exact; reproducing
the *corpus* is not offered and the artifact says so.

**R3 — the fact ledger is the authority, and it is written first.** A seeded
fact is not proof that the generated dialogue states it unambiguously, which is
why the spec demands a human audit. The ledger makes that audit possible: every
conversation names the ledger facts it states, every question names the ledger
fact it asks about, and the audit checks that the named fact is actually
recoverable from the named conversation's text.

**R4 — development and held-out question sets never mix**, and the held-out set
is not read while anything is being tuned.

## Task 2: Score the unanswerable population separately

**Files:**
- Create: `membench/abstention_rate.py`
- Modify: `membench/question_result.py`, `membench/run_track_r.py`,
  `membench/metric_means.py`, `membench/write_run.py`, `membench/cli.py`
- Test: `tests/test_abstention_rate.py`, `tests/test_run_track_r.py`,
  `tests/test_metric_means.py`

**Interfaces:**
- Consumes: `Question.answer_conversation_id: str | None` from Task 1.
- Produces: `QuestionResult.answerable: bool`, `QuestionResult.abstained: bool | None`,
  `abstention_rate(results) -> float | None`.

This is R1 in code. Read `membench/run_applicability.py` before you start: it
holds the reasoning for the last free ride this harness closed, and this task is
the same shape of risk. An unanswerable question whose empty ranking counted as
a hit would hand a perfect score to a system that returns nothing at all.

The rule:
- `answerable` is `False` exactly when `question.answer_conversation_id is None`.
- The four metrics are `None` on every unanswerable row — not because nothing
  was observed, but because they are undefined for it.
- `abstained` is `True` when the ranking is empty, `False` when it is not, and
  `None` on an answerable row, where the question does not arise.
- `metric_means` averages the four metrics over answerable, scored rows only.
- `abstention_rate` is the share of unanswerable rows that abstained, and
  `None` when there are no unanswerable rows.

## Task 5: The fact ledger

**Files:**
- Create: `corpora/corpus-a/ledger.jsonl`, `corpora/corpus-a/GENERATION.md`
- Create: `corpora/corpus-a/README.md`

**Interfaces:**
- Consumes: nothing.
- Produces: the fact records Tasks 6, 7 and 8 derive everything from.

This task writes no code. It writes the authority (R3).

The fictional project: one product team, six named people with stable roles,
nine months, an as-of date of the last day of the ninth month. Invent it whole —
it must not resemble this repository, Atrium, Syntopica or any real client, both
because a corpus that echoes the system under test flatters it and because the
declared bias section already concedes enough.

Each ledger record is one JSON object:

```json
{"fact_id": "f12",
 "statement": "El límite de reintentos del worker de cobros se fija en 3",
 "language": "es",
 "kind": "decision",
 "stated_at": "2026-03-04",
 "effective_from": "2026-03-04",
 "reversed_by": "f31",
 "people": ["ana", "marc"],
 "notes": "Ana propone 5, Marc argumenta 3 por el timeout del proveedor"}
```

- `kind` is one of `decision`, `reversal`, `incident`, `preference`,
  `opinion-change`.
- `reversed_by` names the later fact that overturns this one, or is `null`.
- `stated_at` and `effective_from` are separate fields on purpose: the spec
  requires contradiction questions to distinguish statement time from effective
  time, and "the second version wins" is explicitly not a specification. A
  decision taken in March and effective in May is exactly the case that
  separates a system that models time from one that returns the latest text.

Required content:
- 60–80 facts.
- At least 12 reversal pairs, at least 3 of which have `effective_from` later
  than `stated_at`.
- Both languages substantially represented — neither below 40% of facts. The
  languages are not translations of each other: this is one team that works in
  both, so a fact stated in Spanish is discussed in Spanish.
- Incidents, personal preferences and changes of opinion, not only decisions.

`GENERATION.md` records the instructions the conversations will be written from,
so a reader can see what the corpus was asked to be. `README.md` states what
Corpus A is, that it is synthetic, that it was written by an agent from this
ledger, and R2 verbatim: the report reproduces exactly, the corpus does not
claim to regenerate.

## Task 6: The conversations

**Files:**
- Create: `corpora/corpus-a/corpus.jsonl`

**Interfaces:**
- Consumes: `corpora/corpus-a/ledger.jsonl` from Task 5.
- Produces: the corpus Tasks 7, 8 and 9 read.

~120 conversations over the nine months, in the harness format already used by
`corpora/fixture/corpus.jsonl`: one JSON object per line with
`conversation_id`, `started_at` and `messages` of `role`, `content`,
`timestamp`.

**Write these in batches of about 20 and commit each batch**, so a failed batch
costs one batch. Work chronologically: the corpus is ingested chronologically
and a reversal must come after what it reverses.

Each conversation additionally carries a `states` key listing the `fact_id`s it
states. The harness ignores unknown keys; the audit in Task 7 depends on it.
This is the link that makes a label checkable rather than asserted.

Rules the content must satisfy:
- A conversation that states a fact must state it **recoverably**: a reader who
  has only that conversation can answer the question. A fact alluded to is not
  a fact stated, and this is the single most common way a synthetic corpus ends
  up with labels a human audit rejects.
- Roughly a third of conversations state no ledger fact at all. A corpus where
  every conversation is load-bearing is not a retrieval problem.
- Competing conversations are required: for a labelled fact tagged `overlap`,
  another conversation must discuss the same topic with much of the same
  vocabulary and *not* state the fact. Without them `overlap` is a tag with no
  content and the baseline's score means nothing.
- Language per conversation follows its facts; unlabelled conversations split
  between the two.
- 4–12 messages each, alternating `user` and `assistant`, timestamps in order
  and inside the conversation's day.

- [ ] **Step 1: Write the batches, committing each**
- [ ] **Step 2: Verify structure**

```bash
python3 - <<'EOF'

    assert set(r.get('states',[]))<=facts, r['conversation_id']
```

## Task 7: The question sets

**Files:**
- Create: `corpora/corpus-a/questions-dev.jsonl`,
  `corpora/corpus-a/questions-heldout.jsonl`

**Interfaces:**
- Consumes: the ledger and the corpus.
- Produces: the labelled sets Task 9 scores against.

Two sets that never mix (R4). Development ~80 answerable plus ~12 unanswerable;
held-out ~40 answerable plus ~6 unanswerable. A conversation that answers a
development question must not answer a held-out one.

Each question carries the fields `load_questions` reads — `question_id`,
`question`, `answer_conversation_id`, `strata`, and `as_of` where it is
historical — plus an `asks_about` key naming the ledger `fact_id`. The harness
ignores it; the audit needs it.

Required composition:
- Both languages, neither below 40%. A Spanish question is asked the way a
  person asks, accents included, not as a translated English one.
- At least 20 carrying `temporal-contradiction`, split between asking what is
  true *now* and what was believed *then*. The historical ones carry `as_of`
  and are labelled with the conversation that stated the superseded fact — that
  is the whole point of the stratum, and labelling them with the reversal
  instead is the mistake to avoid.
- The unanswerable questions are about the project and plausibly in scope, and
  the corpus genuinely does not answer them. A question about an unrelated
  subject tests nothing. They carry `answer_conversation_id: null` and no

- The `note` stratum: the spec says it either gets generated notes or is
  removed. **Ruling: it is removed for Corpus A.** This corpus has no notes, and
  tagging conversations as notes to populate a cell would be a fabricated
  stratum. Record the removal in `corpora/corpus-a/README.md` and in the
  audit; every question is therefore tagged `conversation`.
- `overlap` versus `no-overlap` must reflect the corpus as written, which Task 6
  had to build competing conversations for.

## Task 8: The audit, the blind critique, and the freeze

**Files:**
- Create: `corpora/corpus-a/audit.md`
- Create: `corpora/corpus-a/audit_labels.py` (a checked-in check, not a one-off)

**Interfaces:**
- Consumes: ledger, corpus, both question sets.
- Produces: the frozen labels Task 9 and every later run depend on.

This is gate 4 of the spec's five: *"Corpus A labels frozen after the human
audit and the Codex critic pass."* Nothing may be tuned before it passes.

**Part 1 — the mechanical audit.** `audit_labels.py` checks what a machine can:
every `asks_about` fact exists; the labelled conversation's `states` list
actually contains that fact; no question's answer conversation is dated after
its `as_of`; every `temporal-contradiction` question's fact participates in a
reversal pair; the unanswerable questions' facts are genuinely absent. It exits
non-zero on any violation and prints every one. Give it a test.

**Part 2 — the blind Codex critique.** Codex reads the corpus and the questions
**without the ledger and without the labels**, and answers, per question, which
conversation it believes answers it and whether the question is ambiguous or
unanswerable. Blind is the point: a critic shown the label will confirm it.

```bash
codex exec -s read-only -c 'mcp_servers={}' \
  -c mcp_servers.serena.enabled=false -c mcp_servers.serena.required=false \
  -c mcp_servers.atrium.enabled=false -c mcp_servers.atrium.required=false \
  --output-schema corpora/corpus-a/critique-schema.json \
  -o corpora/corpus-a/critique.json \
  "<the prompt: read corpus.jsonl and the questions without labels; for each question name the conversation_id that answers it, or null; flag ambiguous questions and say why>" \
  < /dev/null
```

Every disagreement between Codex and the label is adjudicated in `audit.md` and
resolved one of three ways: the label is wrong and changes; the question is
ambiguous and is rewritten or dropped; or the label is right and Codex missed
it, which is recorded as a legitimate difficulty. A disagreement rate above
roughly 15% means the corpus is ambiguous and Task 6 or 7 needs rework — say so
rather than adjudicating a hundred cases one at a time.

**Part 3 — the human audit and the freeze.** The spec requires a human to audit
the evidence spans and the questions; an agent cannot sign that. Prepare the
audit: `audit.md` carries the mechanical results, the Codex disagreements and
their adjudications, and a sample the human reads. **Stop here and hand it to
the owner for the sign-off** — this is a plan step that genuinely ends with a
human, not a ruling an agent may make. Record the freeze in `audit.md` with the
commit the labels are frozen at, once given.

- [ ] **Step 1: Write `audit_labels.py` and its test, TDD**
- [ ] **Step 2: Run it; fix every violation in the corpus or the questions**
- [ ] **Step 3: Run the blind Codex critique; adjudicate every disagreement**
- [ ] **Step 4: Write `audit.md`; hand it to the owner for sign-off**
- [ ] **Step 5: Commit**

`THRESHOLDS.md` states, for the three starred axes (retrieval quality, cost,
latency) and for them only:
- the star bands 0–5, as numbers;
- that they were derived from the baseline run named by its run id, commit and

- that per-stratum results are descriptive, never a per-stratum star, with cell

- that thresholds are not changed for a run once committed, and changing them
  starts a new run id.
